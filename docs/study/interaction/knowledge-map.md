# AI Agent 知识图谱

本文件把共享对话中的学习内容整理成“概念 -> 机制 -> 工程意义 -> 面试表达”的结构。

## 1. LLM 的本质

### 核心定义

LLM 的本质是在给定上下文条件下预测下一个 token：

```text
P(next_token | context)
```

它不是天然在“验证事实”，也不是直接查询数据库。它的输出来自语言分布概率。

### 为什么能表现出推理能力

LLM 持续预测下一个 token，但训练语料本身包含逻辑、代码、推理、规划和人类表达结构。Transformer 的注意力机制能够建模上下文中的长程依赖，所以连续 token 预测在宏观上呈现出推理、写代码、规划和问答能力。

面试表达：

>
>
> LLM 不是在传统意义上执行符号推理，而是在高维概率空间中逼近人类语言分布。由于训练语料包含大量结构化逻辑，Transformer 又能建模上下文依赖，所以连续 token 预测在宏观上表现出推理和规划能力。

## 2. Hallucination 的机制

### 核心原因

LLM 没有内置真实世界校验机制。当上下文不足、训练数据不完整、问题需要实时事实或事实本身不明确时，模型仍然会输出概率上最像正确答案的 token 序列。

### 机制级表达

幻觉不是模型“故意乱说”，而是模型目标函数与真实性目标不完全一致：

```text
模型优化目标：生成语言上连续、概率高的内容
用户期望目标：生成事实正确的内容
```

两者不总是一致。

面试表达：

> Hallucination 的根源在于 LLM 的目标不是事实校验，而是在给定 context 下生成概率最高的语言序列。当 context 中缺少可靠事实约束时，模型可能生成看起来合理但事实错误的内容。

## 3. RAG

### RAG 是什么

RAG 是 Retrieval-Augmented Generation，即检索增强生成。

基本流程：

```text
用户问题
  -> 检索外部知识源
  -> 得到相关文档片段
  -> 拼进 prompt
  -> LLM 基于新 context 生成回答
```

### RAG 的本质

RAG 不改变模型参数，也不改变模型内部概率计算逻辑。它改变的是 context。

原来：

```text
P(token | 用户问题)
```

加入 RAG 后：

```text
P(token | 用户问题 + 外部检索到的文档)
```

面试表达：

> RAG 通过向 prompt 注入外部检索结果，改变条件概率中的 context，从而引导模型在更受约束的语义空间中生成。它不是增强模型参数，而是改变模型生成时看到的条件。

### 为什么 RAG 能降低幻觉

如果 context 中包含明确事实、精确数字、定义或业务文档，模型生成时就更容易沿着这些事实约束继续生成，而不是依赖训练语料中的模糊分布。

### RAG 的核心难点

RAG 的难点不只是“调用向量数据库”，而是让进入 context 的内容既相关又足够精确。

关键环节：

- 文档解析。
- chunk 切分。
- embedding。
- top-k 召回。
- rerank 精排。
- prompt 拼接。
- 引用与答案生成。

## 4. Chunk 策略

### Chunk 太小的问题

chunk 太小会导致语义不完整。模型拿到的片段可能缺少前后文，虽然命中了关键词，但无法支持完整回答。

典型问题：

- 事实断裂。
- 定义缺少上下文。
- 召回结果碎片化。
- LLM 需要自行补全缺失信息，幻觉风险上升。

### Chunk 太大的问题

chunk 太大会导致语义过宽。一个 chunk 包含太多主题，向量表示被稀释，召回时可能看起来相关但噪声很多。

典型问题：

- 召回不精确。
- context 被无关内容占满。
- 成本上升。
- LLM 注意力被干扰。

### 工程判断

chunk 策略的目标不是“越细越好”或“越大越好”，而是在语义完整性和检索精度之间做平衡。

## 5. Top-k

### Top-k 的作用

top-k 控制从向量数据库中取回多少个候选文档片段。

### 权衡

top-k 太小：

- 可能漏掉关键资料。
- 召回率不足。

top-k 太大：

- 噪声增加。
- prompt 变长。
- 成本上升。
- 模型更容易被无关上下文干扰。

工程表达：

> top-k 是召回率与上下文噪声之间的权衡，不是越大越好。

## 6. Rerank

### 为什么需要 rerank

embedding 检索解决的是粗粒度语义相似，但语义相似不等于任务相关。

例子：

用户问：“如何解决 Redis 内存淘汰问题？”

向量检索可能召回：

- Redis 内存结构介绍。
- Redis 为什么快。
- Redis 内存淘汰策略。

这些都语义相关，但真正能回答问题的是内存淘汰策略。

### Rerank 的机制

rerank 通常用 cross-encoder 或 LLM 对 `query + chunk` 做更精细的逐对相关性判断。

面试表达：

> rerank 用于解决向量检索“语义相关但任务不相关”的问题。embedding 负责粗排，rerank 通过对 query 和候选文档做更精细的匹配判断，把真正能支持回答的内容排到前面。

## 7. Memory

### Memory 的价值

如果没有 Memory，Agent 在多轮任务中只能基于当前输入做局部决策，容易忘记前文目标、用户偏好和任务状态，导致任务偏离。

面试表达：

> 如果没有 Memory，Agent 无法维持跨步骤的状态信息，每一步决策都会变成基于不完整上下文的局部最优选择，从而在多步任务中出现偏离或失败。

### Memory 的类型

1. Conversation Memory
   - 用户说过什么。
   - 当前对话上下文。

2. State Memory
   - 当前任务执行到哪一步。
   - 已完成哪些 action。
   - 下一步需要什么。

3. Long-term Memory
   - 用户偏好。
   - 历史结果。
   - 可复用经验。

## 8. RAG 与 Memory 的区别

不能简单说：

```text
RAG = 知识
Memory = 状态
```

因为 Memory 里也可能存长期知识或用户偏好。

更本质的区分是它们进入 context 的机制不同：

- RAG 是查询驱动的外部检索。
- Memory 是过程驱动的状态沉淀。

面试表达：

> RAG 是按需检索的外部信息注入机制，它在每次推理前动态获取与当前问题最相关的知识；Memory 是持续累积的上下文管理机制，用于在多步任务中维持状态和历史。两者都会影响 context，但 RAG 是查询驱动，Memory 是过程驱动。

判断例子：

- “Redis 为什么快？”适合通过 RAG 获取技术资料。
- “帮我订一份披萨”中的用户位置、饮食偏好、是否已选餐厅，适合进入 Memory。

## 9. Tool Calling

### Tool Calling 是什么

Tool Calling 让模型不只生成文本，还能选择调用外部工具完成动作。

常见工具：

- 搜索。
- 网页抓取。
- 计算器。
- 数据库查询。
- 订单系统。
- 天气 API。
- 内部业务接口。

### 工程边界

模型负责选择意图和参数，系统负责：

- 定义工具 schema。
- 校验参数。
- 执行工具。
- 捕获错误。
- 控制权限。
- 把工具结果回填给模型。

## 10. Agent 架构

### Agent 不是单次 LLM 调用

Agent 是一个让模型参与决策和行动的系统。它通常包含：

- Planner：拆解任务，决定下一步。
- Executor：执行工具或子任务。
- Memory：维护状态和历史。
- RAG：提供外部知识。
- Reflection / Validation：检查结果是否合理。
- Controller / Graph：控制流程、循环和终止条件。

### 多工具 Agent 执行流程

```text
用户输入
  -> Planner 拆解任务
  -> 选择工具
  -> Executor 调用工具
  -> Memory 更新任务状态
  -> RAG 提供知识约束
  -> LLM 生成阶段性或最终答案
  -> Reflection 校验
  -> 返回结果或重试
```

## 11. Agent 失控与约束

Agent 可能失控的原因：

- 目标不清晰。
- 工具结果不可靠。
- 没有最大循环次数。
- 没有错误处理。
- 没有状态管理。
- 模型反复计划但不终止。

工程约束：

- 最大步数。
- 最大重试次数。
- 工具白名单。
- 参数校验。
- 权限控制。
- 人工确认。
- Reflection 评分。
- 日志与 trace。

## 12. 工程化与部署

你已有的 K8s 与微服务经验可以转化成 AI 工程能力：

- Agent API 服务化。
- 模型 Provider 抽象。
- 推理服务部署。
- 工具服务隔离。
- 向量数据库与关系数据库部署。
- 异步任务处理。
- 日志、监控、trace。
- 成本控制。
- 超时、重试、降级。

面试表达：

> AI Agent 工程不是把 LLM 接进项目就结束，真正难点是把不稳定、昂贵、慢速、依赖外部服务的模型能力，包装成可观测、可降级、可扩展、成本可控的后端系统。

## 13. 大模型服务中的缓存命中

### 缓存命中是什么

缓存命中不是一个单一概念。在大模型服务里，网络上常说的“缓存命中”通常可能指三类东西：

1. KV Cache 命中
   - 发生在模型推理引擎内部。
   - 复用已经计算过的 attention key/value。
   - 主要减少重复上下文的 prefilling 计算。

2. Prompt / Prefix Cache 命中
   - 发生在模型服务层或推理平台层。
   - 如果多个请求有相同的 prompt 前缀，比如相同 system prompt、相同工具说明、相同长文档上下文，平台可以复用这段前缀的 KV Cache。
   - 很多 API 厂商说的 prompt caching，核心就是复用相同前缀。

3. 业务层缓存命中
   - 发生在应用系统里。
   - 缓存 RAG 检索结果、工具调用结果、完整 LLM 响应、embedding 结果等。
   - 更接近传统后端里的 Redis / 本地缓存 / CDN 思路。

所以听到“命中率”时，必须先问清楚：

```text
命中的是哪一层缓存？
是模型内部 KV Cache，还是服务层 prompt cache，还是业务层结果缓存？
```

### 为什么需要缓存

LLM 服务的主要成本来自两部分：

- prefill：处理输入 prompt，把上下文 token 编码进模型状态。
- decode：逐 token 生成输出。

长 prompt 的 prefill 很贵。Agent 和 RAG 场景尤其明显，因为 prompt 里经常包含：

- system prompt。
- 工具 schema。
- 历史对话。
- RAG 检索片段。
- 业务规则。
- 输出格式要求。

如果这些前缀在多次请求中重复，重新计算就是浪费。缓存命中可以减少重复计算。

### KV Cache 的机制

Transformer 在生成时，每一层 attention 都会计算 key 和 value。对于已经处理过的 token，这些 key/value 不需要每次重新算，可以缓存起来。

简化理解：

```text
第一次处理长上下文：
prompt tokens -> 计算 hidden states -> 生成每层 KV -> 存入缓存

后续生成新 token：
复用已有 KV -> 只计算新 token 相关部分
```

这就是为什么同一个请求内部生成多个 token 时，推理引擎一定会用 KV Cache。否则每生成一个 token 都要重新计算整个上下文，成本会非常高。

### Prompt / Prefix Cache 的机制

Prompt cache 是把 KV Cache 从“单个请求内部复用”扩展到“多个请求之间复用”。

例如很多请求都有相同前缀：

```text
system prompt
+ 工具 schema
+ 输出格式要求
+ 用户自己的问题
```

如果前面三段完全相同，推理服务可以把这段公共前缀的 KV 结果缓存下来。下次请求只需要从不同的用户问题开始继续计算。

命中条件通常比较严格：

- 前缀 token 必须一致。
- 模型版本必须一致。
- 推理配置需要兼容。
- 缓存没有过期或被淘汰。
- 请求被调度到能访问该缓存的节点或缓存集群。

所以 prompt cache 更适合稳定前缀明显的场景，比如：

- 固定 system prompt。
- 固定工具列表和 schema。
- 固定业务规则。
- 多用户共享同一份长文档上下文。

### 业务层缓存的机制

业务层缓存不依赖模型内部实现，由应用自己控制。

常见缓存对象：

- embedding：同一段文档不重复向量化。
- RAG 检索结果：相同 query 或归一化 query 复用 top-k。
- 工具结果：搜索、天气、商品信息等短时间内复用。
- 完整回答：FAQ 类问题可以缓存最终答案。

但业务层缓存必须谨慎，因为 LLM 请求通常包含用户身份、权限、时间、上下文和隐私数据。不能简单把所有 prompt 当 key 缓存。

### 命中率高和低的区别

命中率高意味着：

- 重复计算少。
- 平均延迟更低。
- GPU 利用更有效。
- 单请求成本下降。
- 高并发下吞吐更好。

但命中率高不一定代表系统设计正确。如果缓存了过期知识、错误权限的数据或不该复用的用户上下文，命中率越高，错误传播越快。

命中率低意味着：

- 大量请求都要重新 prefill 或重新调用外部服务。
- 延迟更高。
- 成本更高。
- GPU 或外部 API 压力更大。

但命中率低也不一定是坏事。开放式对话、强个性化、多变工具结果、实时数据查询，本来就很难高命中。此时更应该优化 prompt 长度、检索质量、批处理和模型选择，而不是盲目追求缓存命中率。

### 工程判断

缓存适合复用“稳定、确定、权限安全、短期内不会变化”的内容。

适合缓存：

- 固定 system prompt。
- 工具 schema。
- 公共业务规则。
- 静态文档的 embedding。
- 短 TTL 的工具结果。
- FAQ 的标准答案。

不适合直接缓存：

- 包含用户隐私的完整 prompt。
- 强依赖当前时间的回答。
- 权限不同的 RAG 结果。
- 多轮对话中的临时状态。
- 需要严格实时一致性的业务数据。

面试表达：

> 大模型服务里的缓存命中要分层看。推理引擎内部有 KV Cache，用来复用 attention 的 key/value；服务层可能有 prompt 或 prefix cache，用来复用相同 prompt 前缀的预填充计算；业务层还可以缓存 embedding、RAG 检索结果、工具结果或最终回答。命中率高通常能降低延迟和成本，但缓存必须考虑权限、时效性和上下文隔离，否则会把错误或越权数据稳定地复用出去。
