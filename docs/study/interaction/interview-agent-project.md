# 面试项目：多工具 Agent + AI 推理平台部署

本文件整理共享对话中形成的面试项目方向。主线选择是“多工具 Agent”，Kubernetes 和推理平台能力作为工程化延展点。

## 项目定位

项目主题：

```text
多工具 Agent + AI 推理平台部署
```

核心目标：

- 接收用户自然语言请求。
- 理解用户意图。
- 自动选择并调用工具。
- 利用 RAG 提供知识约束。
- 使用 Memory 保持多轮任务状态。
- 通过 Reflection / Validation 检查结果。
- 用 Docker 和 Kubernetes 部署，支持水平扩展。

## 为什么主线选多工具 Agent

多工具 Agent 更能体现 AI Agent 岗位的核心能力：

- 任务理解。
- 任务拆解。
- 工具选择。
- 工具调用。
- 状态管理。
- 结果校验。
- 失败重试。

Kubernetes 和推理平台能力不单独作为主线，而是作为工程化加分项，因为这样更容易形成完整项目叙事：

```text
我做了一个可执行任务的 AI Agent，并且把它工程化部署到了可扩展平台上。
```

而不是：

```text
我分别做了一个 Agent，又做了一个部署平台。
```

## 面试讲解 6 步

### 第 1 步：项目背景与目标

可以这样讲：

> 这个项目的目标是构建一个多工具 AI Agent。用户通过自然语言提出任务，系统通过 LLM 理解意图、拆解步骤，并根据任务需要调用搜索、计算、业务 API 等工具。为了提高回答可靠性，系统引入 RAG 做外部知识约束，用 Memory 维护多轮任务状态，并通过 Reflection 对结果进行校验。最后整个 Agent 服务通过 Docker 和 Kubernetes 部署，支持水平扩展。

要体现的能力点：

- 你理解 Agent 不是聊天机器人。
- 你理解 Agent 是“模型决策 + 系统执行 + 工程约束”的组合。
- 你能把 AI 能力放进后端工程体系。

### 第 2 步：整体架构

模块划分：

1. 用户接口层
   - Web / CLI / HTTP API / gRPC。
   - 接收请求并转换成 AgentState。

2. Agent 核心层
   - Planner：拆解任务，生成行动计划。
   - Executor：调用工具执行子任务。
   - Memory：保存用户偏好、历史和任务状态。
   - RAG：检索外部知识。
   - Reflection / Validation：校验输出并决定是否重试。

3. 工具层
   - 搜索。
   - 计算器。
   - 网页抓取。
   - 业务 API。
   - 可扩展工具注册表。

4. 知识层
   - 文档解析。
   - chunk。
   - embedding。
   - 向量数据库。
   - top-k。
   - rerank。

5. 部署层
   - Docker 镜像。
   - Kubernetes Deployment。
   - Service / Ingress。
   - 日志、监控、扩缩容。

架构表达：

```text
用户请求
  -> API Layer
  -> AgentState
  -> Planner
  -> RAG / Memory / Tools
  -> Executor
  -> Reflection
  -> Memory Write
  -> 返回结果
```

### 第 3 步：工具与知识集成

工具层重点：

- 工具不是随便让模型调用，而是通过 schema 明确定义。
- 系统负责参数校验、权限控制、超时、错误处理。
- 新工具通过注册表接入，不直接修改 Agent 主流程。

知识层重点：

- 文档进入系统后切成 chunk。
- chunk 经过 embedding 存入向量数据库。
- 查询时通过 top-k 召回候选内容。
- 再通过 rerank 提升任务相关性。
- 最后把高质量上下文注入 prompt。

面试表达：

> RAG 负责给模型提供外部事实约束，Tool Calling 负责让模型能执行动作。两者都进入 Agent 流程，但职责不同：RAG 解决“知道什么”，Tool 解决“能做什么”。

### 第 4 步：执行流程示例

示例用户请求：

```text
帮我查一下明天北京的天气，然后计算最佳出行路线。
```

执行流程：

1. Planner 识别这是一个多步骤任务。
2. Planner 拆成天气查询和路线计算。
3. Executor 调用天气工具获取天气。
4. Executor 调用路线工具计算路线。
5. Memory 记录用户位置、任务状态和中间结果。
6. LLM 汇总工具结果生成回答。
7. Reflection 检查是否遗漏关键信息。
8. 如果合格，返回最终答案；如果不合格，触发有限重试。

要强调：

- 多工具协作。
- 状态流转。
- 终止条件。
- 错误处理。

### 第 5 步：部署与扩展

工程化设计：

- Agent API 用容器部署。
- 工具服务可以独立部署。
- 向量数据库和关系数据库作为外部依赖。
- K8s 通过 Deployment 管理多副本。
- 通过 HPA 根据 CPU、请求量或队列长度扩缩容。
- 通过日志和 trace 观察每次 Agent 执行路径。

性能与稳定性优化：

- 工具调用设置超时。
- RAG 检索结果可缓存。
- 对固定 system prompt、工具 schema 和业务规则使用 prefix cache，降低长 prompt 的 prefill 成本。
- 对 embedding、搜索结果和网页抓取结果做短 TTL 缓存，减少重复外部调用。
- Reflection 设置最大重试次数。
- 外部服务失败时降级返回。
- 对高成本模型调用做限流。

面试表达：

> 我没有把 Agent 当成一次 LLM API 调用，而是把它做成一个可部署、可观测、可扩展的后端服务。模型、工具、检索、记忆和反思都可能失败，所以系统必须有超时、重试、降级和成本控制。

如果面试官追问性能优化，可以补充：

> 我会分层看缓存命中：推理层关注 KV Cache 或 prefix cache，减少重复 prompt 的预填充成本；应用层缓存 embedding、RAG 检索结果和短期工具结果。缓存能降低延迟和成本，但必须按用户、权限和 TTL 做隔离，不能为了命中率牺牲答案正确性和数据安全。

### 第 6 步：工程亮点

可以重点讲这些：

- 工具注册表：新工具可扩展，不影响主流程。
- RAG 优化：chunk、top-k、rerank 提升上下文质量。
- Memory 设计：区分对话历史、任务状态和长期偏好。
- Reflection：用有限重试提高可靠性。
- K8s 部署：多副本、扩缩容、服务治理。
- 缓存优化：区分 KV Cache、prefix cache 和业务层缓存，降低延迟和模型调用成本。
- 安全约束：工具白名单、参数校验、权限控制。

## 2 分钟口述框架

```text
我做的项目是一个多工具 AI Agent 后端系统。

它的目标是让用户通过自然语言完成复杂任务，比如查询信息、调用业务接口、计算结果并生成最终建议。系统不是简单把问题丢给 LLM，而是把一次请求转换成 AgentState，然后由 Planner 拆解任务，由 Executor 调用工具，由 RAG 提供外部知识约束，由 Memory 维护多轮状态，最后通过 Reflection 校验结果。

架构上我把系统拆成 API 层、Agent 核心层、工具层、知识层和部署层。API 层只负责协议转换；Agent 核心负责流程编排；工具层通过 schema 和注册表扩展；知识层负责 chunk、embedding、top-k 和 rerank；部署层用 Docker 和 Kubernetes 支持多副本扩展。

这个项目的重点不是调用一次模型，而是把模型能力工程化。比如工具调用有参数校验和超时，Agent 循环有最大步数，RAG 检索有 rerank，Memory 区分对话历史和任务状态，外部服务失败时可以降级。这样系统既能体现 Agent 的智能调度能力，也具备后端服务需要的稳定性、可观测性和扩展性。
```

## 常见追问

### 1. 你的 Agent 和普通 Chatbot 有什么区别？

普通 Chatbot 主要是基于上下文生成回答。Agent 不只是回答，它会根据目标决定是否调用工具、调用什么工具、如何处理工具结果、是否需要重试，并通过 Memory 维护任务状态。

### 2. Planner 和 Executor 为什么要分开？

Planner 负责决定“做什么”和“按什么顺序做”，Executor 负责“把动作执行出来”。分开后可以让任务拆解、工具执行、错误处理和权限控制更清晰。

### 3. 为什么需要 Memory？

多步任务中，如果没有 Memory，每一步都会只基于当前上下文做局部决策，容易忘记用户偏好、任务目标和已完成步骤。Memory 用来保持跨步骤状态。

### 4. RAG 和 Tool Calling 有什么区别？

RAG 解决“模型需要知道什么”，通过检索外部知识改变 context。Tool Calling 解决“模型需要做什么”，通过调用外部工具获取结果或执行动作。

### 5. Agent 为什么会失控？

常见原因是目标不清晰、工具结果异常、没有最大循环次数、没有失败处理、没有状态约束。工程上需要最大步数、超时、工具白名单、参数校验、Reflection 和日志 trace。

### 6. 为什么要用 K8s 部署？

Agent 服务可能面临并发请求、外部服务依赖、模型调用延迟和成本控制。K8s 可以提供多副本部署、滚动发布、服务发现、扩缩容和故障恢复。
